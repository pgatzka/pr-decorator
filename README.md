# pr-decorator

A GitHub Action that writes a deterministic, marker-delimited summary block into a pull request body: the closing issue reference, the commit list, and a provenance footer.

It edits **only** the text between its own markers. Everything the author wrote outside them is never touched, never reordered and never trimmed — and if the body already says exactly what the action would write, no request is made at all.

## What it writes

The action inserts (or replaces in place) this block:

```markdown
<!-- pr-decorator:start -->
Closes #142

## Commits

- 2026-07-28 09:14 — [`a1b2c3d`](https://github.com/pgatzka/pr-decorator/commit/a1b2c3d4e5f60718293a4b5c6d7e8f9012345678) — @alice — `feat(auth): rotate refresh tokens`
- 2026-07-28 11:02 — [`e4f5a6b`](https://github.com/pgatzka/pr-decorator/commit/e4f5a6b7c8d9e0f1a2b3c4d5e6f708192a3b4c5d) — @bob — `test(auth): cover expiry edge case`

<sub>Generated by pr-decorator · head 9c8d7e6 · 3 commits · times in Europe/Berlin</sub>
<!-- pr-decorator:end -->
```

Piece by piece:

- **`Closes #142`** — derived from the head branch name via `branch-pattern`. Omitted entirely (blank line included) when `issue-link: false`, when the branch name does not match, or when the branch name is longer than 255 characters.
- **`## Commits`** — one bullet per commit, in the pull request's own API list order, never re-sorted. Each bullet is `author date — linked short SHA — author — subject`, with the subject in a code span so nothing in it can act on your repository. Timestamps are `YYYY-MM-DD HH:mm` in the `timezone` you supply, rendered from the **author** date, so a rebase does not restamp the list.
- **The footer** — the head short SHA, the pull request's **total** commit count, and the timezone the timestamps were rendered in. Omitted when `footer: false`.

Commit subjects come from whoever opened the pull request, so they are neutralized before they land: each one is rendered inside a code span, and anything shaped like one of this action's HTML comment markers is removed outright.

The code span is not cosmetic. GitHub's closing-keyword pass reads the pull request body, so a commit subject saying it fixes an issue would otherwise close that issue the moment the pull request merges — and a backslash escape does **not** stop it, which was measured against live GitHub rather than assumed. A code span does. It is also what keeps a subject from emitting a mention, so nobody is notified because of what someone wrote in a commit message.

The rendered markdown targets GitHub-Flavored Markdown as documented on [docs.github.com](https://docs.github.com/en/get-started/writing-on-github) and in the [Pull requests REST reference](https://docs.github.com/en/rest/pulls/pulls). That is the format authority — not a convention local to this repository.

### Opting a pull request out

Put this line anywhere in the body and the action leaves it completely untouched:

```markdown
<!-- pr-decorator:skip -->
```

## Usage

The recommended workflow. Copy it as-is and change the timezone:

```yaml
name: Decorate pull requests

on:
  pull_request:
    types: [opened, reopened, synchronize, ready_for_review]

permissions:
  pull-requests: write

# Rapid pushes queue several runs on the same pull request, and only the newest
# can produce a correct block. Keyed on the pull request number so runs on
# different pull requests never cancel each other.
concurrency:
  group: pr-decorator-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  decorate:
    runs-on: ubuntu-latest
    steps:
      - uses: pgatzka/pr-decorator@v1
        with:
          timezone: Europe/Berlin
```

There is no `actions/checkout` step, and there does not need to be: the action reads the pull request and its commits through the API and never looks at a working tree.

### Inputs

| Name | Type | Default | Required | Description |
| --- | --- | --- | --- | --- |
| `timezone` | IANA zone name | *none* | **yes** | Zone the commit author timestamps are rendered in, for example `Europe/Berlin`. Deliberately has no default — a guessed zone silently mislabels every timestamp. Offsets such as `UTC+2` are not zone names and are rejected. |
| `token` | string | `${{ github.token }}` | no | Token used to read the pull request and write its body. Needs `pull-requests: write`. |
| `position` | `top` \| `bottom` | `top` | no | Where the block is placed on **first** write. Later runs keep the block wherever it already is, so moving it by hand sticks. |
| `issue-link` | boolean | `true` | no | Emit the `Closes #N` line derived from the head branch name. |
| `branch-pattern` | regular expression | `^(\d+)-` | no | Matched against the head branch name; capture group 1 is read as the issue number. Must declare at least one capturing group, otherwise the run fails at input parsing rather than silently rendering no line. |
| `footer` | boolean | `true` | no | Emit the generated-by footer line at the end of the block. |
| `mentions` | `login` \| `name` | `login` | no | How commit authors are rendered: `login` for `@mentions`, `name` for the plain git author name. |
| `dry-run` | boolean | `false` | no | Render the block and log it without writing to the pull request. |

Booleans accept the spellings the Actions toolkit accepts: `true`, `True`, `TRUE`, `false`, `False`, `FALSE`.

### Outputs

None. v1 deliberately declares no `outputs:`, so a consuming workflow cannot chain a later step on the rendered block. This is a known limitation, recorded as a decision rather than an oversight — adding outputs later is additive and will not require a new major tag.

## Decorating pull requests from forks

A pull request opened from a fork runs with a **read-only** `GITHUB_TOKEN`, no matter what your workflow's `permissions:` block asks for. The write comes back `403`; the action logs a warning explaining why and **exits 0**, leaving the run green with no decoration. Nobody involved can fix that from a `pull_request` workflow — not the contributor, and not you.

The only supported way to decorate them is `pull_request_target`, which runs the workflow from the **base** repository with the base repository's token:

```yaml
name: Decorate pull requests

on:
  pull_request_target:
    types: [opened, reopened, synchronize, ready_for_review]

permissions:
  pull-requests: write

concurrency:
  group: pr-decorator-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  decorate:
    runs-on: ubuntu-latest
    steps:
      # No checkout. See the rule below — this is not an omission.
      - uses: pgatzka/pr-decorator@v1
        with:
          timezone: Europe/Berlin
```

> [!WARNING]
> **Never check out the head ref under `pull_request_target`.**
>
> `pull_request_target` runs with the base repository's **write** token. Adding an `actions/checkout` step with `ref: ${{ github.event.pull_request.head.sha }}` — or any other head-ref checkout — puts a contributor's code on disk inside a job holding that token, and anything that then executes it (a build script, a `postinstall` hook, a linter plugin) runs as you. This action needs no working tree at all: it uses pull request metadata and the API only. Keep the job checkout-free.

## Behavior worth knowing before you enable it

### Re-runs re-mention the commit authors

Every render writes the author field again. With the default `mentions: login` that means `@name` mentions are re-rendered on each write, and GitHub may notify those people again. If that is noisy for your repository, opt out:

```yaml
with:
  timezone: Europe/Berlin
  mentions: name
```

`mentions: name` renders the plain git author name and never emits an `@`.

### A PAT in `token` can start a loop

The default `${{ github.token }}` does **not** trigger further workflow runs — GitHub suppresses that on purpose. A personal access token supplied via `token` **does**. So a workflow that also listens on `edited` will see its own body edit, run again, and can loop.

The only loop guard in this action is the **byte-identical block comparison**: before writing, the body is re-read and the new body is compared to the current one; if they are identical, no request is made and the chain stops. There is deliberately no actor check and no bot-name check — either could be defeated by a self-hosted or renamed identity, whereas the comparison cannot.

In practice: with a PAT, do not put `edited` in your `types:` list.

### Limitations

- **250 commits.** `GET /pulls/{n}/commits` serves at most 250 commits however it is paged, so the list stops there. When it does, the block says so in a `Showing first 250 of N commits.` note, and the footer still reports the pull request's true total.
- **Long bodies.** A pull request body is capped at 65,536 characters. Commits are dropped from the end of the list to fit, and the block reports how many with a `… and N more commits` line. If the author's own text leaves no room for even an empty block, nothing is written and the run warns.
- **Markers are found by line scan, not by parsing markdown.** A marker line pasted inside a fenced code block is indistinguishable from a real one and will be treated as the block. The result is still non-destructive, but it will look wrong.
- **A start marker with no end marker** stops the write: the body is in a state nothing can edit safely, so the action warns and leaves it alone. Restore or remove the stray line.
- **No `outputs:`** — see [Outputs](#outputs).

## Contributing

### The `dist/` conflict protocol

This is a JavaScript action, so the runner executes `dist/index.js`, not `src/`. The bundle is therefore **committed on every pull request**, and CI fails any branch whose `dist/` does not match a fresh `npm run package`.

That makes `dist/index.js` shared mutable state: every branch touching `src/` also touches it, so branches conflict on it whenever they are rebased.

**Never hand-merge and never hand-edit `dist/`.** On a conflict:

1. Take either side of the `dist/` conflict — it does not matter which.
2. Rebase the **source** and resolve the real conflicts in `src/` and `test/`.
3. Re-run `npm run package`.
4. Commit the regenerated bundle.

CI's freshness gate is what proves the result is correct; a hand-merged bundle can be plausible and wrong at the same time, and no review will catch it.

### Local commands

```sh
npm ci
npm run lint      # eslint
npm test          # vitest
npm run build     # tsc --noEmit
npm run package   # rebuild dist/ — commit the result
```

Node 24 is required. The same major is pinned in `package.json` `engines`, in `runs.using` in `action.yml`, and in the CI workflow; a test fails the build if the three drift apart.
